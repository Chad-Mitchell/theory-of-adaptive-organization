## Medium

**M1. Where the round 15 and 16 runs came from.** `RESULTS.md` for rounds 15 and 16 says "from a fresh clone at ed1ceef / c6f01f6". The exact provenance is this. The run directory (`<local>/r15-check`) was cloned once at 05:08:49 EST from upstream main, with a reference to an older local clone. The lock commit was then fetched into it from the local working copy `<local>/r11-fold`, not from GitHub, and the same directory was reused for round 16. The script and PREREG hashes were checked with `sha256sum -c` before each run, so the run tree is identical to the pushed lock. But "pushed before the run" is established only by timestamps, not by a clone of GitHub. For round 16 the push (05:15:41) and the run's START line (05:15:41) fall in the same second, so that ordering holds to one second only. The round 14 runs were started from `<local>/r12-fresh`, which had received 4e189c6 the same way (a local fetch), about 15 seconds after the push at 03:54:43.

**M2. The "box clock stepped" explanation (round 14 `RESULTS.md`, WORKLOG 06:03) is withdrawn.** The box wall clock agreed with GitHub's push times before and after the run (03:54:42, 05:09:12, 05:15:41, 05:21:50 and 06:03:51 EST). What lags is the monotonic (uptime) clock: the kernel boot time reads 03:26:43 while PID 1 dates from 03:20:07, a difference of about 6.6 minutes. A pause of the box during the run (for example a VM suspend) would explain every number: `timeout` counts run time, so it allowed 120 minutes of running, which took about 126.6 minutes of wall time. This cause is a HYPOTHESIS. The two clocks are OBSERVED. The scores do not change: H1 and H2 printed nothing either way, and no limit was extended.

## Process rule for future rounds (from 2026-11-26)

1. Push the lock. 2. Confirm with `git ls-remote <fork> <branch>` that the lock commit is the branch tip or an ancestor of it. 3. Clone from GitHub into a new directory (not from a local working copy) at that commit. 4. Verify the hashes there. 5. Launch from that clone. 6. Put the ls-remote line and the clone path in the run log. A run launched any other way is described exactly, as in M1, and is not described as run "from the pushed lock".
Also: test every helper on toy inputs before the lock, and give a validity check in the PREREG for any step whose failure could print the predicted outcome.
